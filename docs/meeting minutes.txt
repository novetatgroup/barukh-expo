Payments API — UI Integration Guide
Base URL: {{url}}/payments
There are two endpoints. The flow is: call initiate-charge once, then if the response comes back with a nextAction, keep calling next-action until the payment is CAPTURED or FAILED.
1. POST {{url}}/payments/initiate-charge
Kicks off a charge for a shipment.
Request body (CreateTransferRequestDto):
{
  "currency": "USD",
  "shipmentId": "bkh-transfer-1627384950",
  "customerId": "cus_IpH7CKCUtD",
  "paymentMethodId": "pmd_wlVhaYmkl2",
  "amount": 250,
  "redirectUrl": "http://barukh.com/payments/success",
  "meta": {
    "senderId": "1",
    "travellerId": "2",
    "senderName": "King James",
    "travellerName": "Patrick Star",
    "sourceDestination": "paris_kampala"
  }
}All fields are required. shipmentId is what dedupes charges — if you call this twice with the same shipmentId, the backend won't create a second charge; it just returns the current state of the existing one. So it's safe to retry this call if you're unsure whether it went through.
Response (CreateTransferResponseDto):
{
  "status": "success",
  "message": "Transfer initiated",
  "reference": "bkh-<uuid>",
  "paymentStatus": "PENDING",
  "nextAction": {
    "mode": "PIN",
    "url": null,
    "requiresAdditionalFields": []
  }
}
reference — save this. You need it for every subsequent next-action call.
paymentStatus — one of PENDING, CAPTURED, FAILED, CANCELLED, REFUNDED.
nextAction — only present if the charge isn't finished yet. Tells the UI what to do next:
mode: "PIN" → prompt the user for their card PIN, submit it via next-action.
mode: "OTP" → prompt the user for an OTP code.
mode: "ADDITIONAL_FIELDS" → check requiresAdditionalFields for which fields to collect (e.g. authorization.avs.address).
mode: "REDIRECT_URL" → redirect the user to nextAction.url (typically a 3DS auth page).

If nextAction is absent and paymentStatus is CAPTURED, the charge is done — no further calls needed.
2. POST {{url}}/payments/next-action
Used to complete whatever step initiate-charge (or a previous next-action call) asked for.
Request body (NextActionRequestDto):
{
  "reference": "bkh-<uuid-from-initiate-charge>",
  "data": {
    "type": "PIN",
    "pin": "1234"
  }
}data shape depends on which mode you got back:
   mode from previous response data to send     PIN { "type": "PIN", "pin": "1234" }   OTP { "type": "OTP", "otp": "123456" }   ADDITIONAL_FIELDS { "type": "ADDITIONAL_FIELDS", "additionalFields": { ... } }   REDIRECT_URL Don't call this endpoint — just redirect the user to nextAction.url. The redirect flow completes on Flutterwave's side.   Response (NextActionResponseDto) — same shape logic as initiate-charge's response:
{
  "status": "success",
  "message": "Transfer Updated",
  "reference": "bkh-<uuid>",
  "paymentStatus": "CAPTURED",
  "data": {
    "amount": 250,
    "currency": "USD",
    "meta": { "senderId": "1", "travellerId": "2", "senderName": "King James", "travellerName": "Patrick Star", "sourceDestination": "paris_kampala" }
  }
}
If paymentStatus is CAPTURED → done, show success.
If paymentStatus is PENDING and nextAction is present again → loop back, ask the user for the next thing (e.g. PIN then OTP, back to back, is normal).
If paymentStatus is FAILED → show message to the user (it's already a user-friendly string like "Insufficient funds, please try again").


General notes

If a call throws/500s, treat it as a failed attempt and let the user retry — the backend marks the record FAILED internally and logs the reason server-side; you won't get a detailed error message back, just a generic error.
There's an x-test-scenario header both endpoints accept for staging/testing against specific Flutterwave scenarios (e.g. forcing a decline). It's silently ignored in production, so don't rely on it for anything user-facing — it's a QA tool only.
reference is the single source of truth to track a charge across the whole flow — persist it in UI state (or the URL) as soon as you get it from initiate-charge.
